## 1. PURPOSE

This document defines the Decision-Ready Model Foundation for DAO v1.4. It specifies:

- The architecture of Pattern Memory as a learning system
- The decision intelligence loop that connects situations, decisions, outcomes, and lessons
- The graph-ready object model that enables future Decision Memory Graph upgrades
- The Similar Prior Case recognition mechanism
- The post-decision monitoring and drift detection framework
- The option comparison foundation
- What is explicitly deferred to v1.5 / v2.x and why

The goal is to make DAO v1.4 decision-ready without making it decision-heavy. Every component here is designed so that v1.5 upgrades do not require re-architecture — they require only extension.

## 2. THE DECISION INTELLIGENCE LOOP

The full loop that DAO v1.4 must close:

```
┌─────────────────────────────────────────────────────────────────┐
│                   DECISION INTELLIGENCE LOOP                    │
│                                                                 │
│  DATA → SCAN → SITUATION → ACTION → DECISION → OUTCOME         │
│    ↑                                              │             │
│    │         POST-DECISION MONITORING             │             │
│    │              ↑                               │             │
│    │         DRIFT DETECTED?                      ↓             │
│    │              │                           LESSON            │
│    │              │                              │              │
│    └──────── PATTERN MEMORY ←─────────────────── ┘             │
│                   │                                             │
│                   ↓                                             │
│         SIMILAR PRIOR CASE                                      │
│         surfaces in next Situation                              │
└─────────────────────────────────────────────────────────────────┘
```

This is not a future aspiration. Every segment of this loop must be operational in v1.4. The sophistication of each segment scales with scope (see §10), but no segment is absent.

## 3. PATTERN MEMORY ARCHITECTURE

### 3.1 What Pattern Memory Does

Pattern Memory is the institutional intelligence layer of DAO. It does three things:

1. **Recognises:** When a Situation is generated by the Situation Engine, Pattern Memory checks whether this pattern — defined by pattern type and domain — has been seen before.
2. **Surfaces:** If a match is found, the prior case is attached to the Situation object and displayed to the executive.
3. **Learns:** When a decision review is completed and a lesson is captured, Pattern Memory is updated with the new outcome and lesson.

In v1.4, Pattern Memory does not learn autonomously. It learns from completed decision review cycles — when a human confirms what happened, what worked, and what should be done differently. This is by design. Autonomous learning is a v1.5+ capability.

### 3.2 Pattern Record Lifecycle

```
SITUATION DETECTED
  → Situation Engine creates Situation with pattern_detected field
  → Pattern Memory scanned for matching pattern_type + domain
  → If match found: similar_prior_case attached to Situation
  → If no match: situation.similar_prior_case = null

DECISION LOGGED
  → Decision linked to Situation via linked_situation_id
  → Monitoring activated against situation.source_datasets

DECISION REVIEWED
  → Review submitted with verdict, actual_outcome, lesson, variance
  → Pattern tag applied to decision record
  → Pattern Memory updated:
      If existing pattern: add historical_action entry with outcome + lesson
      If new pattern: create new Pattern Record from this situation + decision

PATTERN SURFACING
  → Next time a matching pattern fires, prior case is attached
  → Prior case shows: what was done, what the outcome was, whether reusable
```

### 3.3 Pattern Type Taxonomy

Patterns are classified by type. This taxonomy is the controlled vocabulary for cross-decision recognition. v1.4 launches with these built-in pattern types:

**Operational patterns:**
- `maintenance-deferral` — delayed maintenance leading to efficiency or safety risk
- `capacity-constraint` — resource at >95% utilisation or <60% utilisation
- `process-leak` — rework, exceptions, manual workarounds recurring >3 times in 90 days
- `recurring-failure` — same incident type repeating >3 times in 90 days
- `decision-stall` — decision revisited >3 times without resolution

**Revenue / Financial patterns:**
- `procurement-substitution` — supplier or product switch producing unexpected cost change
- `pricing-leakage` — value delivered without being charged, or discounts without justification
- `relationship-undermonetisation` — customer, partner, or supplier relationship generating below-potential revenue
- `cost-trap` — financial item pending beyond 30 days creating cash flow risk

**Strategic patterns:**
- `expansion-pricing` — aggressive pricing at market entry followed by margin collapse
- `supplier-dependency` — single-source dependency creating production or delivery risk
- `governance-gap` — decisions made repeatedly without adequate challenge or documentation

**Cross-domain patterns:**
- `signal-drift` — KPI or indicator trending negative over multiple reporting cycles
- `stakeholder-misalignment` — conflicting accounts from different functions for the same phenomenon

New pattern types can be added by creating a new entry in the pattern taxonomy. The taxonomy is stored in `src/core/patterns/taxonomy.js` in v1.4.

### 3.4 Pattern Matching Logic in v1.4

In v1.4, pattern matching is based on:
1. `pattern_type` — exact match from taxonomy
2. `domain` — operational / revenue / financial / compliance / cross-domain
3. Recency weighting — more recent prior cases are shown first

Matching is deterministic, not probabilistic, in v1.4. The Situation Engine assigns `pattern_detected` during generation (AI-assisted based on finding analysis). Pattern Memory then performs a lookup on the taxonomy match.

**Not in v1.4:** Semantic similarity matching, fuzzy pattern clustering, cross-pattern inference. These are v1.5+ capabilities.

### 3.5 Pattern Memory — Minimum Viable Seed

Pattern Memory requires prior decisions to be useful. In a fresh deployment with no decision history, Pattern Memory is empty.

To address this in v1.4:
- When a decision review is submitted, it must prompt the user to apply a pattern tag and capture a lesson. This is the primary seeding mechanism.
- The Theory of Mind / Decision Profile (v1.3 capability preserved) contributes to pattern visibility at the individual level.
- Domain modules may seed Pattern Memory with domain-specific starter patterns for the Water domain.

## 4. SIMILAR PRIOR CASE RECOGNITION

### 4.1 Recognition Process

When the Situation Engine creates a Situation, it runs the following process:

```
1. Identify pattern_type from finding analysis
   (AI-assisted via scan prompt output or post-processing)

2. Query Pattern Memory for records where:
   pattern.pattern_type == situation.pattern_detected
   AND pattern.domain == situation.domain
   AND pattern.occurrence_count > 0

3. If match(es) found:
   a. Select the most recent entry from pattern.historical_actions
   b. Assess reuse_recommendation and reuse_confidence
   c. Populate situation.similar_prior_case with:
      - pattern_id
      - title (most recent historical action context)
      - action_taken
      - outcome
      - reusable (true/false based on reuse_confidence)

4. If no match:
   situation.similar_prior_case = null
```

### 4.2 Prior Case Display Rules

The prior case must appear in four locations (from TARGET_SPEC §10.3):

**Location 1 — Situation Panel**
```
SIMILAR PRIOR CASE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[Pattern title] — [Domain] — [Date]
Action taken: [action_taken]
Outcome: [outcome] — [Better / Same / Worse]
Lesson: [lesson]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[Reusable: Yes — Apply this approach] or [Reusable: No — Context has changed]
```

**Location 2 — Executive Situation Brief**
```
PRIOR CASE: [Pattern title] — [outcome in one phrase]
```

**Location 3 — Decision Review Modal**
When reviewing a decision linked to a situation with a prior case:
```
Prior case applied: [pattern title] — Outcome was [Better/Same/Worse]
```

**Location 4 — DAO Chief**
When asked about a situation: DAO Chief must reference the prior case in its response without being asked specifically about prior history.

## 5. POST-DECISION MONITORING AND DRIFT DETECTION

### 5.1 Monitoring Activation Conditions

A decision enters monitoring state when ALL of the following are true:
- `decision.status` = "In Execution" or "Approved"
- `decision.linked_situation_id` is not null
- The linked Situation has at least one `source_dataset` that remains active in the data layer

### 5.2 Drift Classification

When monitoring checks run (on each scan cycle), drift is classified as:

| Classification | Condition |
|---------------|-----------|
| `Better` | KPIs associated with the situation's `causal_chain` show measurable improvement vs baseline |
| `Same` | KPIs within normal variance range (±5% of baseline) |
| `Worse` | KPIs show measurable negative movement vs baseline (>5% degradation on two or more consecutive checks) |
| `Not Yet Assessed` | Insufficient scan cycles since decision was logged (minimum: 2 cycles) |
| `No Data` | Monitoring datasets have been removed or are not returning data |

### 5.3 Drift Response Actions

| Drift result | DAO response |
|-------------|--------------|
| `Better` | Decision Timeline updated. Status moves toward "Outcome Emerging." No escalation. |
| `Same` | No change. Monitoring continues. |
| `Worse` | Decision elevated to Decision Risk Radar. Situation re-evaluated. Escalation check triggered. If pattern match: Pattern Memory's reuse_confidence for the applied action is downgraded. |
| `No Data` | Risk Radar entry: "Monitoring gap — datasets unavailable." No escalation but flagged for attention. |

### 5.4 Monitoring Termination

Monitoring terminates and final outcome is recorded when:
- A decision review is submitted (status moves to Outcome Confirmed or Lesson Captured)
- The executive manually closes the monitoring loop with a final outcome
- 180 days have elapsed without a review being submitted (auto-archive with notification)

## 6. DECISION LIFECYCLE — COMPLETE STATE MACHINE

```
LOGGED
  │
  ├─ [Tier 1: auto] ─────────────────────────┐
  │                                           │
  ├─ [Tier 2+: Challenge Check + Rationale]  │
  │                                           ↓
  └──────────────────────────────────────► APPROVED
                                              │
                                              ↓
                                         IN EXECUTION ← monitoring_active = true
                                              │
                                              │ [Review date reached OR drift detected]
                                              ↓
                                         UNDER REVIEW ← enters Review Queue
                                              │
                                              │ [Review submitted]
                                              ↓
                                       OUTCOME EMERGING
                                              │
                                              │ [Outcome confirmed + lesson captured]
                                              ↓
                                      OUTCOME CONFIRMED
                                              │
                                              │ [Lesson captured + pattern tagged]
                                              ↓
                                       LESSON CAPTURED → Pattern Memory updated
                                              │
                                              │
                                    ┌─────────┴─────────┐
                                    │                   │
                                    ↓                   ↓
                                 CLOSED             REOPENED
                                                       │
                                                       └──────► UNDER REVIEW (loop)
```

### 6.1 Lifecycle Transitions That Update Pattern Memory

| Transition | Pattern Memory action |
|-----------|----------------------|
| LESSON CAPTURED → CLOSED | Create or update Pattern Record with this decision's action, outcome, and lesson |
| LESSON CAPTURED → REOPENED | Note that the applied action was insufficient. Downgrade reuse_confidence on the pattern. |
| Any → WORSE drift | Flag the applied action as producing a negative drift outcome. Update pattern record. |

## 7. OPTION COMPARISON FOUNDATION

### 7.1 Scope in v1.4

Option comparison in v1.4 is lightweight and deterministic. It is not a simulation engine. The three strategic options produced by `/api/copilot` are AI-generated from the situation context — they are not calculated from a model.

This is intentional. The foundation is:
1. The schema for option comparison records is defined and linked to decisions
2. The option selected is logged against the decision record
3. The outcome of the chosen option is captured at review time
4. Future versions can replace the AI generation step with model-driven simulation — the linking schema is already in place

### 7.2 Option Comparison Record

```json
{
  "option_set_id": "OPT-<timestamp-slug>",
  "situation_id": "SIT-001",
  "brief_id": "BRF-001",
  "generated_at": "<ISO timestamp>",
  "generated_by": "api/copilot",

  "options": [
    {
      "option_index": 1,
      "title": "Return to previous supplier",
      "description": "Revert to prior supplier contract immediately. Estimated lead time: 5 days.",
      "tradeoff": "Higher unit cost (+8%) but eliminates concentration variability.",
      "estimated_impact": "Annualised saving vs current: RM 1.2M",
      "selected": false
    }
  ],

  "recommendation": "Option 2 — Adjust dosing protocols. Fastest path to resolution without contract renegotiation.",
  "recommendation_confidence": "High",

  "option_selected_index": 2,
  "selected_at": "<ISO timestamp>",
  "selected_by": "<profile name>",
  "linked_decision_id": "DEC-001"
}
```

### 7.3 What Is Not Built in v1.4

| Deferred capability | Why deferred | What foundation is in place |
|--------------------|--------------|-----------------------------|
| Model-driven outcome probability | Requires training data from closed decision loops — insufficient in v1.4 | Option selected is logged, outcome captured — training data accumulates |
| Cross-decision scenario comparison | Requires Decision Memory Graph traversal | Graph-ready schema defined, linkage IDs in place |
| Confidence-weighted multi-scenario recommendation | Requires simulation engine | Option schema is simulation-ready (fields for probability and impact score added as null in v1.4) |

## 8. GRAPH-READY OBJECT MODEL — v1.4 FOUNDATION

### 8.1 Design Principle

Every major object in DAO v1.4 is designed as a node in a future graph. The ID scheme, foreign key references, and relationship fields defined in DATA_ARCHITECTURE §10 form the edge set of this future graph.

No graph database is used in v1.4. The relationships live in localStorage objects. The schema is identical to what a graph database would store.

### 8.2 The Core Object Graph

```
            DATASET ──used_by──> SCAN
                                  │
                             produced
                                  │
                                  ↓
                             SITUATION ──matches──> PATTERN
                                  │                    ↑
                             prompted                  │
                                  │                learned_from
                                  ↓                    │
                             DECISION ────────────────>│
                                  │
                               has
                                  │
                                  ↓
                              REVIEW
                                  │
                           captures_lesson
                                  │
                                  ↓
                             PATTERN (updated)
```

### 8.3 Object IDs and Foreign Keys — Summary

| Object | Primary key | Key foreign keys |
|--------|------------|-----------------|
| Dataset | `dataset_id` | none |
| Scan | `scan_id` | `datasets_included[]` |
| Situation | `situation_id` | `scan_id`, `source_datasets[]`, `linked_decision`, `similar_prior_case.pattern_id` |
| Decision | `id` (DEC-) | `linked_situation_id`, `linked_datasets[]`, `linked_pattern_id` |
| Review | `id` (REV-) | embedded in Decision |
| Pattern | `pattern_id` | `linked_situations[]`, `linked_decisions[]` |
| Brief | `brief_id` | `scan_id`, `top_situation.situation_id` |
| Option Set | `option_set_id` | `situation_id`, `brief_id`, `linked_decision_id` |

### 8.4 Migration Path to Graph Database (v1.5)

When a graph database backend is introduced in v1.5 or later:

1. Extract all localStorage records for each object type
2. Create graph nodes using the primary keys defined above
3. Traverse foreign key arrays to create directed graph edges
4. No object schema changes required — all relationships are already encoded
5. The storage backend changes; the data model does not

## 9. INSTITUTIONAL MEMORY — WHAT DAO REMEMBERS

### 9.1 Memory Categories in v1.4

| Memory type | How stored | What it enables |
|------------|-----------|----------------|
| Decision memory | Decision Ledger (enhanced schema) | Review queue, drift monitoring, timeline view |
| Pattern memory | Pattern Memory records | Similar Prior Case, Preventative Brief, pattern tags |
| Decision profile | Theory of Mind profile | Understanding of how this executive makes decisions |
| Scan history | Scan records (last 5 per type) | Trend comparison, situation recurrence detection |
| Outcome memory | Review records (embedded in decisions) | Learning loop, pattern update trigger |

### 9.2 What DAO Does Not Remember in v1.4

- Cross-user or cross-organisation patterns (single-user deployment)
- External benchmarks or industry-wide pattern comparisons
- Patterns from before the system was deployed (no historical import in v1.4)

These are v1.5+ capabilities. The schema supports them — the deployment scope does not yet include them.

## 11. DESIGN INTEGRITY CHECK

Before finalising this document, the following questions were reviewed:

**Is Pattern Memory genuinely visible, or just stored?**
It surfaces in four locations (§4.2). It fires proactively at Situation creation. It is not a data store the executive must query. ✅

**Does the learning loop actually close?**
The loop from Lesson Captured → Pattern Memory update → Similar Prior Case in next matching Situation is fully specified (§3.2, §6.1). ✅

**Is the decision state machine complete?**
All transitions from Logged to Closed or Reopened are specified. The reopen loop is included. ✅

**Are the graph-ready foundations genuinely graph-ready?**
All objects have stable IDs and foreign key references. The migration path is specified in §8.4 without schema changes. ✅

**Is drift detection actually observable?**
Drift classification is specified with clear thresholds (§5.2). Drift response actions including Risk Radar elevation are specified (§5.3). The Decision Timeline shows drift status. ✅

**Is anything overstated as a v1.4 capability?**
Simulation, graph visualisation, autonomous learning, and cross-organisation benchmarking are all explicitly deferred in §10. The v1.4 scope is decision-ready, not decision-heavy. ✅
